## Аутентификация и авторизация

Для интеграции сервисов «Интеллектуальный домофон» и «Интеллектуальный шлагбаум» с текущей экосистемой PropDevelopment я обосновываю выбор конкретных протоколов аутентификации/авторизации и модели управления доступом.

## 1. Протокол аутентификации: Mutual TLS (mTLS)

**Выбор:** Взаимная TLS-аутентификация по сертификатам X.509 между серверным API PropDevelopment и API-шлюзом партнёра.

**Обоснование:**
- **Двустороннее доверие:** В отличие от одностороннего TLS, где сертификат предъявляет только сервер, mTLS требует сертификат от клиента (PropDevelopment) и сервера (Партнёр). Это исключает риск подмены легитимного партнёра фишинговым шлюзом (атака типа «человек посередине» на канал связи).
- **Нулевое доверие (Zero Trust):** Сеть между ЦОД PropDevelopment и партнёром априори считается враждебной (особенно в гибридной инфраструктуре). Аутентификация на уровне сертификата гарантирует, что соединение установлено именно с тем хостом, который авторизован корпоративным PKI.
- **Стойкость к перехвату токенов:** mTLS защищает канал, в котором далее будет передаваться токен доступа. Без mTLS любой перехват bearer-токена на сетевом уровне означал бы полную компрометацию.

**Ключевая конфигурация:**
- Сертификаты выпускаются внутренним центром сертификации PropDevelopment.
- Партнёр получает уникальный клиентский сертификат, жёстко привязанный к его IP-адресу (белый список).
- Срок жизни сертификатов — 1 год с обязательной ротацией.

## 2. Протокол авторизации: OAuth 2.0 c расширением Client Credentials Grant

**Выбор:** OAuth 2.0 Client Credentials Flow + JWT-токены с ограниченным scope и временем жизни.

**Обоснование:**
- **Машинное взаимодействие (M2M):** Взаимодействие идёт не от имени конечного пользователя (жильца), а от имени серверного приложения PropDevelopment. Flow Client Credentials предназначен именно для server-to-server сценариев, где нет интерактивного входа пользователя.
- **Предотвращение горизонтальных атак:** Токену назначается точный scope, ограничивающий действие:
  - `domofon:open` — только открытие домофона.
  - `gate:open` — только открытие шлагбаума.
  - `biometry:verify` — только проверка биометрии (без доступа к сырым данным).
- **Короткоживущие токены:** Access Token живёт 5 минут. Refresh Token не используется (при M2M-взаимодействии сервер просто запрашивает новый токен). Это минимизирует окно компрометации.
- **JWT как формат токена:** Токен должен быть подписан для гарантии целостности. Партнёр может локально валидировать подпись без обращений к серверу авторизации на каждый запрос, что снижает задержки для критичных физических действий (открытие двери).

## 3. Модель управления доступом: RBAC

**Выбор**: Role-Based Access Control (RBAC) с иерархическими ролями и статическими разрешениями для принятия решений авторизации на стороне PropDevelopment.

**Обоснование:**
- **Простота реализации:** RBAC проще документировать и аудировать силами одного специалиста.
- **Прозрачность аудита:** Решение бинарно: «Роль X имеет разрешение Y на объект Z». Легко проверяется по матрице доступа.
- **Простота интеграции:** Легко накладывается на существующую доменную структуру.
- **Предсказуемость:** Поведение детерминировано назначенной ролью.
- **Устранение текущих проблем:** Роли с префиксом домена жёстко изолируют видимость.
