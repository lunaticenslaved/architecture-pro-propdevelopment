# 1. Требования к безопасности для интеграции с сервисами партнёра SmartHome

## 1. Управление доступом и аутентификация (Access Control)

| № | Требование | Комментарий |
|---|---|---|
| AC-01 | Доступ к API партнёра должен осуществляться исключительно по защищённому каналу с mutual TLS (mTLS) — двусторонней аутентификацией по сертификатам. | Zero Trust (Never trust, always verify). Исключает риск MITM, выявленный в текущих API PropDevelopment. |
| AC-02 | Авторизация каждого запроса к партнёрскому API должна проверяться по токену с ограниченным временем жизни (OAuth 2.0 + JWT), содержащему scope только для конкретного действия (открытие двери, проверка номера). | Principle of Least Privilege. Предотвращает горизонтальное перемещение, подобное инциденту «партнёр из одной УК видит данные другой УК». |
| AC-03 | Взаимодействие между мобильным приложением собственника и партнёрским сервисом должно идти через серверный SmartHome Service. Прямые вызовы из приложения к партнёру запрещены. | Privacy by Design. Скрывает внутренние эндпоинты партнёра от внешней сети и конечного пользователя. |
| AC-04 | Управление правами доступа жильцов (назначение разрешений на въезд / вход) должно происходить исключительно через сервер PropDevelopment, а не напрямую в системе партнёра. | Data Governance. Обеспечивает единый контур управления мастер-данными, устраняя проблему децентрализованной регистрации клиента. |

## 2. Требования к защите персональных и биометрических данных (Data Protection)

| № | Требование | Комментарий |
|---|---|---|
| DP-01 | Биометрические данные (слепки лица, номера автомобилей) являются специальной категорией ПДн. | PropDevelopment обязан получить отдельное письменное согласие собственника на их обработку до первой регистрации в системе.	152-ФЗ, ст. 11. Устраняет риск штрафов, заявленный в цели аудита «проверить соответствие требованиям законодательства». |
| DP-02 | Передача команд и метаданных (статус «открыто/закрыто», время) между PropDevelopment и партнёром должна быть зашифрована (TLS 1.3). Персональные данные (номер авто, идентификатор лица) внутри пакетов должны быть зашифрованы на уровне приложения (JSON Web Encryption). | Шифрование на всех уровнях (Defense in Depth). Противодействует угрозе перехвата, так как контроль передачи данных сейчас «не системный». |
| DP-03 | Реализовать механизм немедленного отзыва биометрических данных и прав доступа по требованию собственника (через мобильное приложение) с гарантированной синхронизацией к партнёру в течение 30 секунд. | Права субъекта ПДн (152-ФЗ, ст. 14). Повышение удовлетворённости клиентов (бизнес-цель). |
| DP-05 | Запрещено использование биометрических данных жильцов для обучения (ML-дообучения) моделей распознавания партнёром без явного отдельного согласия. | Data Governance / GDPR-like лучшие практики. ML-развитие PropDevelopment не должно строиться на неправомерных данных. |

## 3. Требования к безопасности API и интеграционного шлюза (API Security)

| № | Требование | Комментарий |
|---|---|---|
| API-01 | Все API-контракты с партнёром должны проходить обязательный Security Review (проверку ИБ-специалистом) до подписания. Контракты должны строго определять состав полей. | Secure SDLC. Прямое требование из урока по проблеме: «контракты API содержат категории данных, которые явно предоставляют ПДн». |
| API-02 | Партнёр обязан предоставить sandbox-среду, полностью изолированную от реальных устройств домофонов и шлагбаумов. Нагрузочное тестирование и фаззинг проводятся только там. | Security by Design. Не допускает повторения инцидентов с искажением команд в реальных системах ЖКУ. |
| API-03 | Rate limiting (ограничение частоты запросов) и защита от подбора (brute-force). 3 неверные попытки открытия шлагбаума подряд блокируют возможность на 5 минут. | Defence in Depth. Защита от атак на физическое проникновение. |
| API-04 | Все события, переданные через API (открытие/закрытие, отказ в доступе, нераспознанное лицо), должны журналироваться в SIEM PropDevelopment в режиме реального времени. | Инцидент-менеджмент (ГОСТ Р 57580). Закрывает «слепую зону» мониторинга, критичную для физической безопасности. |

## 4. Требования к инфраструктуре IoT и сегментации (Infrastructure Security)

| № | Требование | Комментарий |
|---|---|---|
| INF-01 | Устройства «Умного домофона» и «Шлагбаума» должны быть подключены к строго изолированной технологической сети (VLAN), отделённой от Wi-Fi жильцов и корпоративной сети офиса. | Network Segmentation. Устранение рисков Ранга 3 — «Отсутствие изоляции критических физических систем». |
| INF-02 | Запрещена возможность прямого доступа из интернета к конечным устройствам (IP-адресам домофонов). Доступ только через API-шлюз партнёра, по белому списку IP-адресов.	Zero Trust / SASE-подход. Противодействие компрометации IoT-устройств в гибридной инфраструктуре. |
| INF-03 | Обновление прошивок контроллеров домофонов и шлагбаумов должно производиться централизованно через защищённый канал с контролем целостности (цифровая подпись). | Integrity Control. Блокирует атаку типа подмена прошивки для открытия. |

## 5. Требования к эксплуатации и инцидентам (Operational Security)

| № | Требование | Комментарий |
|---|---|---|
| OPS-01 | Партнёр обязан предоставить SLA реакции на инциденты: реагирование на недоступность сервиса — 15 минут, на утечку биометрии — 1 час (согласно 152-ФЗ — 24 часа на уведомление РКН, но начало реагирования немедленно). | Регуляторный комплаенс (Приказ ФСТЭК №21). |
| OPS-02 | В случае расторжения договора партнёр обязан гарантированно и безвозвратно удалить все персональные и биометрические данные жильцов в течение 30 дней с актом об уничтожении. | 152-ФЗ, ст. 21. + Право на забвение. Закрытие риск-фактора утечек через бывших подрядчиков. |
| OPS-03 | PropDevelopment обязан хранить логи всех действий с замками и шлагбаумами в неизменяемом хранилище (log vault) в течение 1 года для расследования инцидентов физической безопасности. | Инцидент-менеджмент. Анализ повторных проникновений. |
